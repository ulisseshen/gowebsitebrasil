O projeto Go recebe contribuições de todos.

Este documento é um guia para ajudá-lo no processo de contribuição para o projeto Go, que é um pouco diferente daquele usado por outros projetos open source. Assumimos que você tenha um conhecimento básico de Git e Go.

Além das informações aqui, a comunidade Go mantém uma página wiki CodeReview. Sinta-se à vontade para contribuir com a wiki conforme aprende o processo de revisão.

Note que o front end gccgo fica em outro lugar; veja Contributing to gccgo.

Becoming a contributor

Overview

O primeiro passo é registrar-se como um contribuidor Go e configurar seu ambiente. Aqui está um checklist dos passos necessários a seguir:

  • Step 0: Decida qual conta Google você usará para contribuir com Go. Use essa conta para todos os passos seguintes e certifique-se de que git esteja configurado para criar commits com o endereço de e-mail dessa conta.
  • Step 1: Assine e envie um CLA (Contributor License Agreement).
  • Step 2: Configure credenciais de autenticação para o repositório Git do Go. Visite go.googlesource.com, clique em "Generate Password" no menu superior direito da página e siga as instruções.
  • Step 3: Registre-se no Gerrit, a ferramenta de revisão de código usada pela equipe Go, visitando esta página. O CLA e o registro precisam ser feitos apenas uma vez para sua conta.
  • Step 4: Instale git-codereview executando go install golang.org/x/review/git-codereview@latest

Se preferir, há uma ferramenta automatizada que percorre esses passos. Basta executar: 

$ go install golang.org/x/tools/cmd/go-contrib-init@latest
$ cd /code/to/edit
$ go-contrib-init

O restante deste capítulo elabora essas instruções. Se você completou os passos acima (manualmente ou através da ferramenta), pule para Before contributing code.

Step 0: Select a Google Account

Uma contribuição para Go é feita através de uma conta Google com um endereço de e-mail específico. Certifique-se de usar a mesma conta durante todo o processo e para todas as suas contribuições subsequentes. Você pode precisar decidir se usará um endereço pessoal ou corporativo. A escolha dependerá de quem será o proprietário dos direitos autorais do código que você escreverá e enviará. Você pode querer discutir este tópico com seu empregador antes de decidir qual conta usar.

Contas Google podem ser contas de e-mail Gmail, contas de organização G Suite ou contas associadas a um endereço de e-mail externo. Por exemplo, se você precisa usar um e-mail corporativo existente que não é gerenciado através do G Suite, você pode criar uma conta associada com seu endereço de e-mail existente.

Você também precisa garantir que sua ferramenta Git esteja configurada para criar commits usando seu endereço de e-mail escolhido. Você pode configurar o Git globalmente (como padrão para todos os projetos), ou localmente (para um único projeto específico). Você pode verificar a configuração atual com este comando: 

$ git config --global user.email  # check current global config
$ git config user.email           # check current local config

Para mudar o endereço configurado: 

$ git config --global user.email name@example.com   # change global config
$ git config user.email name@example.com            # change local config

Step 1: Contributor License Agreement

Antes de enviar sua primeira mudança para o projeto Go você deve ter completado um dos dois CLAs a seguir. Qual CLA você deve assinar depende de quem possui os direitos autorais do seu trabalho.

  • Se você é o detentor dos direitos autorais, precisará concordar com o individual contributor license agreement, que pode ser completado online.
  • Se sua organização é a detentora dos direitos autorais, a organização precisará concordar com o corporate contributor license agreement.

Você pode verificar seus acordos assinados atualmente e assinar novos no site Google Developers Contributor License Agreements. Se o detentor dos direitos autorais para sua contribuição já completou o acordo em conexão com outro projeto open source do Google, ele não precisa ser completado novamente.

Se o detentor dos direitos autorais para o código que você está enviando mudar—por exemplo, se você começar a contribuir código em nome de uma nova empresa—envie um e-mail para a golang-dev mailing list. Isso nos permitirá saber a situação para que possamos garantir que um acordo apropriado seja completado.

Step 2: Configure git authentication

O repositório principal do Go está localizado em go.googlesource.com, um servidor Git hospedado pelo Google. A autenticação no servidor web é feita através de sua conta Google, mas você também precisa configurar git no seu computador para acessá-lo. Siga estes passos:

  1. Visite go.googlesource.com e clique em "Generate Password" no menu superior direito da página. Você será redirecionado para accounts.google.com para fazer login.
  2. Após fazer login, você será levado a uma página com o título "Configure Git". Esta página contém um script personalizado que quando executado localmente configurará o Git para armazenar sua chave de autenticação única. Esta chave é pareada com uma que é gerada e armazenada no servidor, análoga a como as chaves SSH funcionam.
  3. Copie e execute este script localmente em seu terminal para armazenar seu token de autenticação secreto em um arquivo .gitcookies. Se você estiver usando um computador Windows e executando cmd, você deve seguir as instruções na caixa amarela para executar o comando; caso contrário, execute o script regular.

Step 3: Create a Gerrit account

Gerrit é uma ferramenta open-source usada pelos mantenedores do Go para discutir e revisar envios de código.

Para registrar sua conta, visite go-review.googlesource.com/login/ e faça login uma vez usando a mesma conta Google que você usou acima.

Step 4: Install the git-codereview command

Mudanças no Go devem ser revisadas antes de serem aceitas, não importa quem faça a mudança. Um comando git personalizado chamado git-codereview simplifica o envio de mudanças para o Gerrit.

Instale o comando git-codereview executando, 

$ go install golang.org/x/review/git-codereview@latest

Certifique-se de que git-codereview esteja instalado no path do seu shell, para que o comando git possa encontrá-lo. Verifique que 

$ git codereview help

imprime texto de ajuda, não um erro. Se imprimir um erro, certifique-se de que $GOPATH/bin esteja no seu $PATH.

No Windows, ao usar git-bash você deve garantir que git-codereview.exe esteja no seu git exec-path. Execute git --exec-path para descobrir a localização correta e então crie um link simbólico ou apenas copie o executável de $GOPATH/bin para este diretório.

Before contributing code

O projeto recebe patches de código, mas para garantir que as coisas sejam bem coordenadas você deve discutir qualquer mudança significativa antes de iniciar o trabalho. É recomendado que você sinalize sua intenção de contribuir no issue tracker, seja criando uma nova issue ou reivindicando uma existente.

Where to contribute

O projeto Go consiste no repositório principal go, que contém o código fonte para a linguagem Go, bem como muitos repositórios golang.org/x/.... Estes contêm as várias ferramentas e infraestrutura que suportam Go. Por exemplo, golang.org/x/pkgsite é para pkg.go.dev, golang.org/x/playground é para o Go playground, e golang.org/x/tools contém uma variedade de ferramentas Go, incluindo o servidor de linguagem Go, gopls. Você pode ver uma lista de todos os repositórios golang.org/x/... em go.googlesource.com.

Check the issue tracker

Se você já sabe qual contribuição fazer, ou está procurando por uma ideia, o issue tracker é sempre o primeiro lugar a ir. Issues são triadas para categorizá-las e gerenciar o fluxo de trabalho.

A maioria dos repositórios golang.org/x/... também usa o issue tracker principal do Go. No entanto, alguns desses repositórios gerenciam suas issues separadamente, então certifique-se de verificar o tracker correto para o repositório ao qual você gostaria de contribuir.

A maioria das issues será marcada com um dos seguintes rótulos de fluxo de trabalho:

  • NeedsInvestigation: A issue não está totalmente compreendida e requer análise para entender a causa raiz.
  • NeedsDecision: a issue é relativamente bem compreendida, mas a equipe Go ainda não decidiu a melhor maneira de abordá-la. Seria melhor esperar por uma decisão antes de escrever código. Se você está interessado em trabalhar em uma issue neste estado, sinta-se à vontade para "pingar" os mantenedores nos comentários da issue se algum tempo passou sem uma decisão.
  • NeedsFix: a issue é totalmente compreendida e o código pode ser escrito para corrigi-la.

Você pode usar a funcionalidade de busca do GitHub para encontrar issues para ajudar. Exemplos:

  • Issues que precisam de investigação: is:issue is:open label:NeedsInvestigation
  • Issues que precisam de correção: is:issue is:open label:NeedsFix
  • Issues que precisam de correção e têm uma mudança sugerida: is:issue is:open label:NeedsFix ("golang.org/cl" OR "go.dev/cl")
  • Issues que precisam de correção e não têm uma mudança sugerida: is:issue is:open label:NeedsFix NOT "golang.org/cl" NOT "go.dev/cl"

Open an issue for any new problem

Excluindo mudanças muito triviais, todas as contribuições devem estar conectadas a uma issue existente. Sinta-se à vontade para abrir uma e discutir seus planos. Este processo dá a todos a chance de validar o design, ajuda a prevenir duplicação de esforço, e garante que a ideia se encaixa nos objetivos para a linguagem e ferramentas. Também verifica se o design é sólido antes do código ser escrito; a ferramenta de revisão de código não é o lugar para discussões de alto nível.

Ao planejar o trabalho, note que o projeto Go segue um ciclo de desenvolvimento de seis meses para o repositório principal do Go. A segunda metade de cada ciclo é um congelamento de features de três meses durante o qual apenas correções de bugs e atualizações de documentação são aceitas. Novas contribuições podem ser enviadas durante um congelamento de features, mas elas não serão mescladas até que o congelamento termine. O congelamento se aplica a todo o repositório principal bem como ao código nos repositórios golang.org/x/... que é necessário para construir os binários incluídos no release. Veja as listas de pacotes vendored na biblioteca padrão e no comando go.

Mudanças significativas na linguagem, bibliotecas ou ferramentas (que incluem mudanças de API no repositório principal e todos os repositórios golang.org/x, bem como mudanças de linha de comando no comando go) devem passar pelo processo de proposta de mudança antes de poderem ser aceitas.

Issues sensíveis relacionadas à segurança (apenas!) devem ser relatadas para security@golang.org.

Sending a change via GitHub

Contribuidores iniciantes que já estão familiarizados com o fluxo do GitHub são encorajados a usar o mesmo processo para contribuições Go. Embora os mantenedores do Go usem Gerrit para revisão de código, um bot chamado Gopherbot foi criado para sincronizar pull requests do GitHub com o Gerrit.

Abra um pull request do GitHub como você normalmente faria. Gopherbot criará uma change list (uma "CL") correspondente no Gerrit e postará um link para ela no seu pull request do GitHub; atualizações no pull request também serão refletidas na CL do Gerrit. Quando alguém comentar na CL, o comentário também será postado no seu pull request, então você receberá uma notificação.

Algumas coisas para ter em mente:

  • Você precisará de uma conta Gerrit para responder aos seus revisores, incluindo para marcar feedback como 'Done' se implementado conforme sugerido. É uma boa ideia familiarizar-se com o Gerrit, como navegar pelas CLs abertas, inscrever-se para atualizações em CLs interessantes (via o ícone de estrela), ou revisar ou dar um +1 para CLs de outras pessoas.
  • Para atualizar o pull request com novo código, apenas faça push para o branch; você pode adicionar mais commits, ou fazer rebase e force-push (ambos os estilos são aceitos).
  • Se a solicitação for aceita, todos os commits serão squashed, e a descrição final do commit será composta concatenando o título e descrição do pull request. As descrições dos commits individuais serão descartadas. Veja Writing good commit messages para algumas sugestões.
  • Veja o FAQ para mais detalhes.

Sending a change via Gerrit

Não é possível sincronizar completamente Gerrit e GitHub, pelo menos no momento, então recomendamos aprender Gerrit. É diferente, mas poderoso, e familiaridade com ele ajudará você a entender o fluxo.

As seções a seguir dão um breve passo a passo de enviar uma mudança via Gerrit. Para mais detalhes sobre interagir com Gerrit, consulte documentação do Gerrit. Em particular, recomendamos ler a Review UI Overview e Basic Gerrit Walkthrough — For GitHub Users.

Overview

Esta é uma visão geral do processo geral:

  • Step 1: Clone o código fonte de go.googlesource.com e certifique-se de que está estável compilando e testando uma vez.

    Se você está fazendo uma mudança no repositório principal do Go:

    $ git clone https://go.googlesource.com/go
$ cd go/src
$ ./all.bash                                # compile and test

    Se você está fazendo uma mudança em um dos repositórios golang.org/x/... (golang.org/x/tools, neste exemplo): 

    $ git clone https://go.googlesource.com/tools
$ cd tools
$ go test ./...                             # compile and test
  • Step 2: Prepare mudanças em um novo branch, criado a partir do branch master. Para fazer commit das mudanças, use git codereview change; isso criará ou modificará um único commit no branch. 
    $ git checkout -b mybranch
$ [edit files...]
$ git add [files...]
$ git codereview change   # create commit in the branch
$ [edit again...]
$ git add [files...]
$ git codereview change   # amend the existing commit with new changes
$ [etc.]
  • Step 3: Teste suas mudanças, executando os testes no pacote que você editou ou re-executando all.bash.

    No repositório principal do Go:

    $ ./all.bash    # recompile and test

    Em um repositório golang.org/x/...:

    $ go test ./... # recompile and test
  • Step 4: Envie as mudanças para revisão no Gerrit usando git codereview mail (que não usa e-mail, apesar do nome). 
    $ git codereview mail     # send changes to Gerrit
  • Step 5: Após uma revisão, aplique mudanças ao mesmo único commit e envie-as para o Gerrit novamente: 
    $ [edit files...]
$ git add [files...]
$ git codereview change   # update same commit
$ git codereview mail     # send to Gerrit again

O restante desta seção descreve esses passos em mais detalhes.

Step 1: Clone the source code

Além de uma instalação recente do Go, você precisa ter uma cópia local do código fonte clonada do repositório correto. Você pode clonar o repositório de código fonte do Go no seu sistema de arquivos local em qualquer lugar que quiser, desde que esteja fora do seu GOPATH (padrão é o diretório go no seu diretório home). Clone de go.googlesource.com (não do GitHub):

Repositório principal do Go:

$ git clone https://go.googlesource.com/go
$ cd go

repositório golang.org/x/...

(golang.org/x/tools neste exemplo): 
$ git clone https://go.googlesource.com/tools
$ cd tools

Step 2: Prepare changes in a new branch

Cada mudança no Go deve ser feita em um branch separado, criado a partir do branch master. Você pode usar os comandos normais do git para criar um branch e adicionar mudanças à área de staging: 

$ git checkout -b mybranch
$ [edit files...]
$ git add [files...]

Para fazer commit das mudanças, em vez de git commit, use git codereview change. 

$ git codereview change
(open $EDITOR)

Você pode editar a descrição do commit no seu editor favorito como de costume. O comando git codereview change adicionará automaticamente uma linha Change-Id única perto do final. Essa linha é usada pelo Gerrit para corresponder uploads sucessivos da mesma mudança. Não edite ou delete ela. Um Change-Id se parece com isto: 

Change-Id: I2fbdbffb3aab626c4b6f56348861b7909e3e8990

A ferramenta também verifica se você executou go fmt sobre o código fonte, e se a mensagem do commit segue o formato sugerido.

Se você precisar editar os arquivos novamente, pode fazer stage das novas mudanças e re-executar git codereview change: cada execução subsequente modificará o commit existente enquanto preserva o Change-Id.

Certifique-se de sempre manter um único commit em cada branch. Se você adicionar mais commits por engano, pode usar git rebase para squash them together em um único.

Step 3: Test your changes

Você escreveu e testou seu código, mas antes de enviar código para revisão, execute todos os testes para toda a árvore para garantir que as mudanças não quebrem outros pacotes ou programas.

In the main Go repository

Para pacotes da biblioteca padrão, todos os testes dentro do pacote devem passar: 

$ go test

A suíte de testes curta para toda a árvore pode ser executada com all.bash (Para construir no Windows use all.bat): 

$ cd go/src
$ ./all.bash

Após executar por um tempo e imprimir muita saída de testes, o comando deve terminar imprimindo, 

ALL TESTS PASSED

Você pode usar make.bash em vez de all.bash para apenas construir o compilador e a biblioteca padrão sem executar a suíte de testes. Uma vez que a ferramenta go seja construída, ela será instalada como bin/go sob o diretório no qual você clonou o repositório Go, e você pode executá-la diretamente de lá. Veja também a seção sobre como testar suas mudanças rapidamente.

In the golang.org/x/... repositories

Execute os testes para todo o repositório (golang.org/x/tools, neste exemplo): 

$ cd tools
$ go test ./...

Se você está preocupado com o status da build, pode verificar o Build Dashboard. Falhas de teste também podem ser detectadas pelos TryBots na revisão de código.

Alguns repositórios, como golang.org/x/vscode-go terão infraestruturas de teste diferentes, então sempre verifique a documentação para o repositório no qual você está trabalhando. O arquivo README na raiz do repositório geralmente terá essas informações.

Step 4: Send changes for review

Uma vez que a mudança esteja pronta e testada em toda a árvore, envie-a para revisão. Isso é feito com o sub-comando mail que, apesar do nome, não envia e-mail diretamente; apenas envia a mudança para o Gerrit: 

$ git codereview mail

O Gerrit atribui um número e URL à sua mudança, que git codereview mail imprimirá, algo como: 

remote: New Changes:
remote:   https://go-review.googlesource.com/99999 math: improved Sin, Cos and Tan precision for very large arguments

Se você receber um erro, verifique a seção Troubleshooting mail errors.

Se sua mudança se relaciona a uma issue aberta do GitHub e você seguiu o formato de mensagem de commit sugerido, a issue será atualizada em alguns minutos por um bot, linkando sua mudança do Gerrit a ela nos comentários.

Step 5: Revise changes after a review

Mantenedores do Go revisarão seu código no Gerrit, e você receberá notificações via e-mail. Você pode ver a revisão no Gerrit e comentar nelas lá. Você também pode responder usando e-mail se preferir.

Se você precisar revisar sua mudança após a revisão, edite os arquivos no mesmo branch que você criou anteriormente, adicione-os à área de staging do Git, e então modifique o commit com git codereview change: 

$ git codereview change     # amend current commit
(open $EDITOR)
$ git codereview mail       # send new changes to Gerrit

Se você não precisar mudar a descrição do commit, apenas salve e saia do editor. Lembre-se de não tocar na linha especial Change-Id.

Novamente, certifique-se de sempre manter um único commit em cada branch. Se você adicionar mais commits por engano, pode usar git rebase para squash them together em um único.

Good commit messages

Mensagens de commit no Go seguem um conjunto específico de convenções, que discutimos nesta seção.

Aqui está um exemplo de uma boa mensagem: 

math: improve Sin, Cos and Tan precision for very large arguments

The existing implementation has poor numerical properties for
large arguments, so use the McGillicutty algorithm to improve
accuracy above 1e10.

The algorithm is described at https://wikipedia.org/wiki/McGillicutty_Algorithm

Fixes #159

First line

A primeira linha da descrição da mudança é convencionalmente um resumo curto de uma linha da mudança, prefixado pelo pacote primário afetado.

Uma regra prática é que deve ser escrita para completar a frase "This change modifies Go to _____." Isso significa que não começa com letra maiúscula, não é uma frase completa, e realmente resume o resultado da mudança.

Siga a primeira linha por uma linha em branco.

Main content

O resto da descrição elabora e deve fornecer contexto para a mudança e explicar o que ela faz. Escreva em frases completas com pontuação correta, assim como para seus comentários em Go. Não use HTML, Markdown ou qualquer outra linguagem de marcação.

Adicione qualquer informação relevante, como dados de benchmark se a mudança afetar performance. A ferramenta benchstat é convencionalmente usada para formatar dados de benchmark para descrições de mudanças.

Referencing issues

A notação especial "Fixes #12345" associa a mudança com a issue 12345 no issue tracker do Go. Quando esta mudança for eventualmente aplicada, o issue tracker marcará automaticamente a issue como corrigida.

Se a mudança é um passo parcial em direção à resolução da issue, escreva "Updates #12345" em vez disso. Isso deixará um comentário na issue linkando de volta à mudança no Gerrit, mas não fechará a issue quando a mudança for aplicada.

Se você está enviando uma mudança contra um repositório golang.org/x/..., você deve usar a sintaxe totalmente qualificada suportada pelo GitHub para garantir que a mudança seja linkada à issue no repositório principal, não no repositório x/. A maioria das issues é rastreada no issue tracker do repositório principal. A forma correta é "Fixes golang/go#159".

The review process

Esta seção explica o processo de revisão em detalhes e como abordar revisões após uma mudança ter sido enviada.

Common beginner mistakes

Quando uma mudança é enviada para o Gerrit, geralmente é triada dentro de alguns dias. Um mantenedor dará uma olhada e fornecerá alguma revisão inicial que para contribuidores iniciantes geralmente se concentra em cosmética básica e erros comuns. Isso inclui coisas como:

  • Mensagem de commit não seguindo o formato sugerido.
  • A falta de uma issue do GitHub linkada. A grande maioria das mudanças requer uma issue linkada que descreve o bug ou a feature que a mudança corrige ou implementa, e um consenso deve ter sido alcançado no tracker antes de prosseguir com ela. Revisões do Gerrit não discutem o mérito da mudança, apenas sua implementação.
    Apenas mudanças triviais ou cosméticas serão aceitas sem uma issue associada.
  • Mudança enviada durante a fase de congelamento do ciclo de desenvolvimento, quando a árvore está fechada para mudanças gerais. Neste caso, um mantenedor pode revisar o código com uma linha como R=go1.12, o que significa que será revisado mais tarde quando a árvore abrir para uma nova janela de desenvolvimento. Você pode adicionar R=go1.XX como um comentário você mesmo se souber que não é o período de tempo correto para a mudança.

Trybots

Após uma leitura inicial da sua mudança, mantenedores acionarão trybots, um cluster de servidores que executará a suíte de testes completa em várias arquiteturas diferentes. A maioria dos trybots completa em alguns minutos, momento em que um link será postado no Gerrit onde você pode ver os resultados.

Se a execução do trybot falhar, siga o link e verifique os logs completos das plataformas nas quais os testes falharam. Tente entender o que quebrou, atualize seu patch para corrigir, e faça upload novamente. Mantenedores acionarão uma nova execução do trybot para ver se o problema foi corrigido.

Às vezes, a árvore pode estar quebrada em algumas plataformas por algumas horas; se a falha relatada pelo trybot não parecer relacionada ao seu patch, vá ao Build Dashboard e verifique se a mesma falha aparece em outros commits recentes na mesma plataforma. Neste caso, sinta-se à vontade para escrever um comentário no Gerrit para mencionar que a falha não está relacionada à sua mudança, para ajudar os mantenedores a entender a situação. Você também pode pesquisar issues do GitHub pela mensagem de erro falhando ou navegar issues watchflakes atualizadas recentemente. Se sua mudança é baseada em um commit mais antigo ou parece que alguém mais já corrigiu o problema, tente fazer rebase para o último commit master via git rebase.

Reviews

A comunidade Go valoriza revisões muito minuciosas. Pense em cada comentário de revisão como um ticket: espera-se que você de alguma forma o "feche" agindo sobre ele, seja implementando a sugestão ou convencendo o revisor do contrário.

Após você atualizar a mudança, percorra os comentários de revisão e certifique-se de responder a todos. Você pode clicar no botão "Done" para responder indicando que você implementou a sugestão do revisor; caso contrário, clique em "Reply" e explique por que você não o fez, ou o que você fez em vez disso.

É perfeitamente normal que mudanças passem por várias rodadas de revisões, com um ou mais revisores fazendo novos comentários toda vez e então esperando por uma mudança atualizada antes de revisar novamente. Este ciclo acontece até mesmo para contribuidores experientes, então não se desencoraje com isso.

Voting conventions

Conforme se aproximam de uma decisão, revisores aplicarão um voto de Code-Review à sua mudança. Há dois votos possíveis:

  • +2 A mudança é aprovada para ser mesclada. Apenas mantenedores do Go (também chamados de "approvers") podem dar um voto +2.
  • +1 A mudança parece boa, mas ou o revisor está solicitando mudanças menores antes de aprová-la, ou eles não são um mantenedor e não podem aprovar, mas gostariam de encorajar uma aprovação.

Para ser submetida, uma mudança deve ter um Code-Review +2 de um mantenedor.

Mantenedores também podem aplicar um voto Hold +1 à mudança, para marcar uma mudança que não deve ser submetida agora (por exemplo, porque a revisão de proposta para nova API na mudança não foi completada).

Para ser submetida, uma mudança não deve ter nenhum voto Hold +1 de um mantenedor.

Finalmente, para ser submetida, uma mudança deve ter o envolvimento de dois funcionários do Google, seja como o uploader da mudança ou como um revisor votando pelo menos Code-Review +1. Este requisito é por razões de compliance e segurança da cadeia de suprimentos.

Submitting an approved change

Quando uma mudança estiver pronta, um mantenedor submeterá a mudança, o que a adiciona como um commit ao repositório Gerrit.

Os dois passos (aprovar e submeter) são separados porque em alguns casos mantenedores podem querer aprovar mas não submeter imediatamente (por exemplo, a árvore poderia estar temporariamente congelada).

Submeter uma mudança a adiciona ao repositório. A descrição da mudança incluirá um link para a revisão de código, que será atualizada com um link para a mudança no repositório. Como o método usado para integrar as mudanças é o "Cherry Pick" do Git, os hashes de commit no repositório serão alterados pela operação de submit.

Se sua mudança foi aprovada há alguns dias sem ser submetida, sinta-se à vontade para escrever um comentário no Gerrit solicitando submissão.

Miscellaneous topics

Esta seção coleta vários outros comentários que estão fora do processo issue/edit/code review/submit em si.

Gopls

Ao trabalhar no repositório principal do Go e usar gopls com seu editor, o comando go invocado pelo gopls deve corresponder à versão do código fonte em que você está trabalhando. O comando go pode ser construído com make.bash e o diretório bin deve ser adicionado ao seu PATH. Veja Gopls: Advanced topics para detalhes adicionais.

Documentação completa para Gopls pode ser encontrada em https://go.dev/gopls.

Copyright headers

Arquivos no repositório Go não listam nomes de autores, tanto para evitar desordem quanto para evitar ter que manter as listas atualizadas. Em vez disso, seu nome aparecerá no change log.

Novos arquivos que você contribuir devem usar o cabeçalho de copyright padrão: 

// Copyright {{now.UTC.Year}} The Go Authors. All rights reserved.
// Use of this source code is governed by a BSD-style
// license that can be found in the LICENSE file.

Arquivos no repositório têm copyright do ano em que são adicionados. Não atualize o ano de copyright em arquivos que você mudar.

Troubleshooting mail errors

A maneira mais comum pela qual o comando git codereview mail falha é porque o endereço de e-mail no commit não corresponde ao que você usou durante o processo de registro.
Se você ver algo como... 

remote: Processing changes: refs: 1, done
remote:
remote: ERROR:  In commit ab13517fa29487dcf8b0d48916c51639426c5ee9
remote: ERROR:  author email address XXXXXXXXXXXXXXXXXXX
remote: ERROR:  does not match your user account.

você precisa configurar o Git para este repositório usar o endereço de e-mail com o qual você se registrou. Para mudar o endereço de e-mail para garantir que isso não aconteça novamente, execute: 

$ git config user.email email@address.com

Então mude o commit para usar este endereço de e-mail alternativo com este comando: 

$ git commit --amend --author="Author Name <email@address.com>"

Então tente novamente executando: 

$ git codereview mail

Quickly testing your changes

Executar all.bash para cada mudança individual na árvore de código é oneroso. Embora seja fortemente sugerido executá-lo antes de enviar uma mudança, durante o ciclo de desenvolvimento normal você pode querer compilar e testar apenas o pacote que está desenvolvendo.

  • Em geral, você pode executar make.bash em vez de all.bash para apenas reconstruir a toolchain do Go sem executar toda a suíte de testes. Ou você pode executar run.bash para apenas executar toda a suíte de testes sem reconstruir a toolchain. Você pode pensar em all.bash como make.bash seguido por run.bash.
  • Nesta seção, chamaremos o diretório no qual você clonou o repositório Go de $GOROOT. A ferramenta go construída por $GOROOT/src/make.bash será instalada em $GOROOT/bin/go e você pode invocá-la para testar seu código. Por exemplo, se você modificou o compilador e quer testar como isso afeta a suíte de testes do seu próprio projeto, apenas execute go test usando-o: 
    $ cd <MYPROJECTDIR>
$ $GOROOT/bin/go test
  • Se você está mudando a biblioteca padrão, provavelmente não precisa reconstruir o compilador: você pode apenas executar os testes para o pacote que mudou. Você pode fazer isso com a versão Go que você normalmente usa, ou com o compilador Go construído a partir do seu clone (o que é às vezes necessário porque o código da biblioteca padrão que você está modificando pode requerer uma versão mais nova do que a estável que você tem instalada). 
    $ cd $GOROOT/src/crypto/sha1
$ [make changes...]
$ $GOROOT/bin/go test .
  • Se você está modificando o compilador em si, pode apenas recompilar a ferramenta compile (que é o binário interno invocado por go build para compilar cada pacote individual). Depois disso, você vai querer testá-lo compilando ou executando algo. 
    $ cd $GOROOT/src
$ [make changes...]
$ $GOROOT/bin/go install cmd/compile
$ $GOROOT/bin/go build [something...]   # test the new compiler
$ $GOROOT/bin/go run [something...]     # test the new compiler
$ $GOROOT/bin/go test [something...]    # test the new compiler
    O mesmo se aplica a outras ferramentas internas da toolchain do Go, como asm, cover, link, e assim por diante. Apenas recompile e instale a ferramenta usando go install cmd/<TOOL> e então use o binário Go construído para testá-la.
  • Além dos testes padrão por pacote, há uma suíte de testes de nível superior em $GOROOT/test que contém vários testes black-box e de regressão. A suíte de testes é executada por all.bash mas você também pode executá-la manualmente: 
    $ $GOROOT/bin/go test cmd/internal/testdir

Specifying a reviewer / CCing others

A menos que explicitamente dito o contrário, como na discussão que levou ao envio da mudança, é melhor não especificar um revisor. Todas as mudanças são automaticamente colocadas em CC na lista de e-mail golang-codereviews@googlegroups.com. Se esta é sua primeira mudança, pode haver um atraso de moderação antes de aparecer na lista de e-mail, para prevenir spam.

Você pode especificar um revisor ou colocar partes interessadas em CC usando as opções -r ou -cc. Ambas aceitam uma lista de endereços de e-mail separados por vírgulas: 

$ git codereview mail -r joe@golang.org -cc mabel@example.com,math-nuts@swtch.com

Synchronize your client

Enquanto você estava trabalhando, outros podem ter submetido mudanças para o repositório. Para atualizar seu branch local, execute 

$ git codereview sync

(Por baixo dos panos isso executa git pull -r.)

Reviewing code by others

Como parte do processo de revisão, revisores podem propor mudanças diretamente (no fluxo do GitHub isso seria alguém mais anexando commits a um pull request). Gerrit fornece acesso a comandos que ajudarão você a importar mudanças propostas por outro desenvolvedor para que você possa revisar/testá-las localmente. Da página Gerrit para a CL que você quer importar, abra o menu "⋮", clique no link "Download patch". Dependendo do seu fluxo de trabalho git preferido, escolha o comando apropriado. As opções ficarão algo assim: 

$ git fetch https://go.googlesource.com/review refs/changes/21/13245/1 && git checkout FETCH_HEAD

Para reverter, mude de volta para o branch em que você estava trabalhando.

Set up git aliases

O comando git-codereview pode ser executado diretamente do shell digitando, por exemplo, 

$ git codereview sync

mas é mais conveniente configurar aliases para os próprios subcomandos do git-codereview, para que o acima se torne, 

$ git sync

Os subcomandos do git-codereview foram escolhidos para serem distintos dos próprios do Git, então é seguro definir esses aliases. Para instalá-los, copie este texto no seu arquivo de configuração do Git (geralmente .gitconfig no seu diretório home): 

[alias]
	change = codereview change
	gofmt = codereview gofmt
	mail = codereview mail
	pending = codereview pending
	submit = codereview submit
	sync = codereview sync

Sending multiple dependent changes

Usuários avançados podem querer empilhar commits relacionados em um único branch. Gerrit permite que mudanças dependam umas das outras, formando tal cadeia de dependência. Cada mudança precisará ser aprovada e submetida separadamente, mas a dependência será visível para os revisores.

Para enviar um grupo de mudanças dependentes, mantenha cada mudança como um commit diferente sob o mesmo branch, e então execute: 

$ git codereview mail HEAD

Certifique-se de especificar explicitamente HEAD, que geralmente não é necessário ao enviar mudanças únicas. Mais detalhes podem ser encontrados na documentação do git-codereview.
