Introdução

Data races estão entre os tipos de bugs mais comuns e mais difíceis de depurar em sistemas concorrentes. Uma data race ocorre quando duas goroutines acessam a mesma variável concorrentemente e pelo menos um dos acessos é uma escrita. Veja O Modelo de Memória do Go para detalhes.

Aqui está um exemplo de uma data race que pode levar a crashes e corrupção de memória: 

func main() {
	c := make(chan bool)
	m := make(map[string]string)
	go func() {
		m["1"] = "a" // First conflicting access.
		c <- true
	}()
	m["2"] = "b" // Second conflicting access.
	<-c
	for k, v := range m {
		fmt.Println(k, v)
	}
}

Uso

Para ajudar a diagnosticar tais bugs, Go inclui um detector de data race integrado. Para usá-lo, adicione a flag -race ao comando go: 

$ go test -race mypkg    // to test the package
$ go run -race mysrc.go  // to run the source file
$ go build -race mycmd   // to build the command
$ go install -race mypkg // to install the package

Opções

A variável de ambiente GORACE define opções do race detector. O formato é: 

GORACE="option1=val1 option2=val2"

As opções são:

  • log_path (padrão stderr): O race detector escreve seu relatório para um arquivo chamado log_path.pid. Os nomes especiais stdout e stderr fazem com que relatórios sejam escritos para saída padrão e erro padrão, respectivamente.
  • exitcode (padrão 66): O status de saída a usar ao sair após uma race detectada.
  • strip_path_prefix (padrão ""): Remove este prefixo de todos os caminhos de arquivo reportados, para tornar relatórios mais concisos.
  • history_size (padrão 1): O histórico de acesso à memória por goroutine é 32K * 2**history_size elementos. Aumentar este valor pode evitar um erro "failed to restore the stack" em relatórios, ao custo de uso aumentado de memória.
  • halt_on_error (padrão 0): Controla se o programa sai após reportar a primeira data race.
  • atexit_sleep_ms (padrão 1000): Quantidade de milissegundos para dormir na goroutine principal antes de sair.

Exemplo: 

$ GORACE="log_path=/tmp/race/report strip_path_prefix=/my/go/sources/" go test -race

Excluindo Testes

Quando você compila com a flag -race, o comando go define uma build tag adicional race. Você pode usar a tag para excluir algum código e testes ao executar o race detector. Alguns exemplos: 

// +build !race

package foo

// The test contains a data race. See issue 123.
func TestFoo(t *testing.T) {
	// ...
}

// The test fails under the race detector due to timeouts.
func TestBar(t *testing.T) {
	// ...
}

// The test takes too long under the race detector.
func TestBaz(t *testing.T) {
	// ...
}

Como Usar

Para começar, execute seus testes usando o race detector (go test -race). O race detector apenas encontra races que acontecem em tempo de execução, então ele não pode encontrar races em caminhos de código que não são executados. Se seus testes têm cobertura incompleta, você pode encontrar mais races executando um binário compilado com -race sob uma carga de trabalho realista.

Data Races Típicas

Aqui estão algumas data races típicas. Todas elas podem ser detectadas com o race detector.

Race no contador de loop

func main() {
	var wg sync.WaitGroup
	wg.Add(5)
	var i int
	for i = 0; i < 5; i++ {
		go func() {
			fmt.Println(i) // Not the 'i' you are looking for.
			wg.Done()
		}()
	}
	wg.Wait()
}

A variável i na função literal é a mesma variável usada pelo loop, então a leitura na goroutine compete com o incremento do loop. (Este programa tipicamente imprime 55555, não 01234.) O programa pode ser corrigido fazendo uma cópia da variável: 

func main() {
	var wg sync.WaitGroup
	wg.Add(5)
	var i int
	for i = 0; i < 5; i++ {
		go func(j int) {
			fmt.Println(j) // Good. Read local copy of the loop counter.
			wg.Done()
		}(i)
	}
	wg.Wait()
}

Variável compartilhada acidentalmente

// ParallelWrite writes data to file1 and file2, returns the errors.
func ParallelWrite(data []byte) chan error {
	res := make(chan error, 2)
	f1, err := os.Create("file1")
	if err != nil {
		res <- err
	} else {
		go func() {
			// This err is shared with the main goroutine,
			// so the write races with the write below.
			_, err = f1.Write(data)
			res <- err
			f1.Close()
		}()
	}
	f2, err := os.Create("file2") // The second conflicting write to err.
	if err != nil {
		res <- err
	} else {
		go func() {
			_, err = f2.Write(data)
			res <- err
			f2.Close()
		}()
	}
	return res
}

A correção é introduzir novas variáveis nas goroutines (note o uso de :=): 

			...
			_, err := f1.Write(data)
			...
			_, err := f2.Write(data)
			...

Variável global desprotegida

Se o código a seguir é chamado de várias goroutines, ele leva a races no map service. Leituras e escritas concorrentes do mesmo map não são seguras: 

var service map[string]net.Addr

func RegisterService(name string, addr net.Addr) {
	service[name] = addr
}

func LookupService(name string) net.Addr {
	return service[name]
}

Para tornar o código seguro, proteja os acessos com um mutex: 

var (
	service   map[string]net.Addr
	serviceMu sync.Mutex
)

func RegisterService(name string, addr net.Addr) {
	serviceMu.Lock()
	defer serviceMu.Unlock()
	service[name] = addr
}

func LookupService(name string) net.Addr {
	serviceMu.Lock()
	defer serviceMu.Unlock()
	return service[name]
}

Variável primitiva desprotegida

Data races podem acontecer em variáveis de tipos primitivos também (bool, int, int64, etc.), como neste exemplo: 

type Watchdog struct{ last int64 }

func (w *Watchdog) KeepAlive() {
	w.last = time.Now().UnixNano() // First conflicting access.
}

func (w *Watchdog) Start() {
	go func() {
		for {
			time.Sleep(time.Second)
			// Second conflicting access.
			if w.last < time.Now().Add(-10*time.Second).UnixNano() {
				fmt.Println("No keepalives for 10 seconds. Dying.")
				os.Exit(1)
			}
		}
	}()
}

Até tais data races "inocentes" podem levar a problemas difíceis de depurar causados por não-atomicidade dos acessos à memória, interferência com otimizações do compilador, ou problemas de reordenação ao acessar memória do processador.

Uma correção típica para esta race é usar um channel ou um mutex. Para preservar o comportamento lock-free, também pode-se usar o package sync/atomic. 

type Watchdog struct{ last int64 }

func (w *Watchdog) KeepAlive() {
	atomic.StoreInt64(&w.last, time.Now().UnixNano())
}

func (w *Watchdog) Start() {
	go func() {
		for {
			time.Sleep(time.Second)
			if atomic.LoadInt64(&w.last) < time.Now().Add(-10*time.Second).UnixNano() {
				fmt.Println("No keepalives for 10 seconds. Dying.")
				os.Exit(1)
			}
		}
	}()
}

Operações send e close não sincronizadas

Como este exemplo demonstra, operações send e close não sincronizadas no mesmo channel também podem ser uma condição de corrida: 

c := make(chan struct{}) // or buffered channel

// The race detector cannot derive the happens before relation
// for the following send and close operations. These two operations
// are unsynchronized and happen concurrently.
go func() { c <- struct{}{} }()
close(c)

De acordo com o modelo de memória do Go, um send em um channel acontece antes do receive correspondente daquele channel completar. Para sincronizar operações send e close, use uma operação receive que garanta que o send é feito antes do close: 

c := make(chan struct{}) // or buffered channel

go func() { c <- struct{}{} }()
<-c
close(c)

Requisitos

O race detector requer que cgo esteja habilitado, e em sistemas não-Darwin requer um compilador C instalado. O race detector suporta linux/amd64, linux/ppc64le, linux/arm64, linux/s390x, linux/loong64, freebsd/amd64, netbsd/amd64, darwin/amd64, darwin/arm64, e windows/amd64.

No Windows, o runtime do race detector é sensível à versão do compilador C instalado; a partir do Go 1.21, compilar um programa com -race requer um compilador C que incorpore a versão 8 ou posterior das bibliotecas de runtime do mingw-w64. Você pode testar seu compilador C invocando-o com os argumentos --print-file-name libsynchronization.a. Um compilador C mais recente e compatível imprimirá um caminho completo para esta biblioteca, enquanto compiladores C mais antigos apenas ecoarão o argumento.

Overhead de Runtime

O custo da detecção de race varia por programa, mas para um programa típico, o uso de memória pode aumentar em 5-10x e o tempo de execução em 2-20x.

O race detector atualmente aloca 8 bytes extras por declaração defer e recover. Essas alocações extras não são recuperadas até que a goroutine saia. Isso significa que se você tem uma goroutine de longa duração que está periodicamente emitindo chamadas defer e recover, o uso de memória do programa pode crescer sem limite. Essas alocações de memória não aparecerão na saída de runtime.ReadMemStats ou runtime/pprof.
