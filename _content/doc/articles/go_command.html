A distribuição Go inclui um comando, chamado "go", que automatiza o download, compilação, instalação e teste de packages e comandos Go. Este documento fala sobre por que escrevemos um novo comando, o que ele é, o que ele não é, e como usá-lo.

Motivação

Você pode ter visto palestras iniciais de Go nas quais Rob Pike brinca que a ideia para Go surgiu enquanto esperava um grande servidor do Google compilar. Aquela realmente foi a motivação para Go: construir uma linguagem que funcionasse bem para construir o grande software que o Google escreve e executa. Ficou claro desde o início que tal linguagem deveria fornecer uma maneira de expressar dependências entre bibliotecas de código claramente, daí o agrupamento de packages e os blocos de import explícitos. Também ficou claro desde o início que você pode querer sintaxe arbitrária para descrever o código sendo importado; é por isso que caminhos de import são literais de string.

Um objetivo explícito para Go desde o início era ser capaz de compilar código Go usando apenas as informações encontradas no próprio source, não precisando escrever um makefile ou um dos muitos substitutos modernos para makefiles. Se Go precisasse de um arquivo de configuração para explicar como compilar seu programa, então Go teria falhado.

No início, não havia compilador Go, e o desenvolvimento inicial focou em construir um e então construir bibliotecas para ele. Por conveniência, adiamos a automação de compilar código Go usando make e escrevendo makefiles. Quando compilar um único package envolvia múltiplas invocações do compilador Go, até usamos um programa para escrever os makefiles para nós. Você pode encontrá-lo se cavar através do histórico do repositório.

O propósito do novo comando go é nosso retorno a este ideal, que programas Go devem compilar sem configuração ou esforço adicional por parte do desenvolvedor além de escrever as declarações de import necessárias.

Configuração versus convenção

A maneira de alcançar a simplicidade de um sistema livre de configuração é estabelecer convenções. O sistema funciona apenas na medida em que essas convenções são seguidas. Quando lançamos Go pela primeira vez, muitas pessoas publicaram packages que tinham que ser instalados em certos lugares, sob certos nomes, usando certas ferramentas de build, para serem usados. Isso é compreensível: é assim que funciona na maioria das outras linguagens. Nos últimos anos, lembramos consistentemente as pessoas sobre o comando goinstall (agora substituído por go get) e suas convenções: primeiro, que o caminho de import é derivado de uma maneira conhecida da URL do código fonte; segundo, que o lugar para armazenar os sources no sistema de arquivos local é derivado de uma maneira conhecida do caminho de import; terceiro, que cada diretório em uma árvore source corresponde a um único package; e quarto, que o package é compilado usando apenas informações no código fonte. Hoje, a vasta maioria dos packages segue essas convenções. O ecossistema Go é mais simples e mais poderoso como resultado.

Recebemos muitas solicitações para permitir um makefile em um diretório de package para fornecer apenas um pouco de configuração extra além do que está no código fonte. Mas isso teria introduzido novas regras. Como não acedemos a tais solicitações, fomos capazes de escrever o comando go e eliminar nosso uso de make ou qualquer outro sistema de build.

É importante entender que o comando go não é uma ferramenta de build geral. Ele não pode ser configurado e não tenta compilar nada além de packages Go. Essas são suposições simplificadoras importantes: elas simplificam não apenas a implementação mas também, mais importante, o uso da própria ferramenta.

Convenções do Go

O comando go requer que o código adira a algumas convenções chave, bem estabelecidas.

Primeiro, o caminho de import é derivado de uma maneira conhecida da URL do código fonte. Para Bitbucket, GitHub, Google Code e Launchpad, o diretório raiz do repositório é identificado pela URL principal do repositório, sem o prefixo https://. Subdiretórios são nomeados adicionando a esse caminho. Por exemplo, o código fonte do package de logging do Google glog é obtido executando

git clone https://github.com/golang/glog
e assim o caminho de import do package glog é "github.com/golang/glog".

Esses caminhos são meio longos, mas em troca obtemos um namespace automaticamente gerenciado para caminhos de import e a habilidade para uma ferramenta como o comando go olhar para um caminho de import desconhecido e deduzir de onde obter o código fonte.

Segundo, o lugar para armazenar sources no sistema de arquivos local é derivado de uma maneira conhecida do caminho de import, especificamente $GOPATH/src/<import-path>. Se não definido, $GOPATH padroniza para um subdiretório chamado go no diretório home do usuário. Se $GOPATH está definido para uma lista de caminhos, o comando go tenta <dir>/src/<import-path> para cada um dos diretórios naquela lista.

Cada uma dessas árvores contém, por convenção, um diretório de nível superior chamado "bin", para conter executáveis compilados, e um diretório de nível superior chamado "pkg", para conter packages compilados que podem ser importados, e o diretório "src", para conter arquivos fonte de package. Impor esta estrutura nos permite manter cada uma dessas árvores de diretório autocontidas: a forma compilada e os sources estão sempre próximos um do outro.

Essas convenções de nomeação também nos permitem trabalhar na direção reversa, de um nome de diretório para seu caminho de import. Este mapeamento é importante para muitos dos subcomandos do comando go, como veremos abaixo.

Terceiro, cada diretório em uma árvore source corresponde a um único package. Ao restringir um diretório a um único package, não temos que criar caminhos de import híbridos que especificam primeiro o diretório e então o package dentro daquele diretório. Além disso, a maioria das ferramentas de gerenciamento de arquivos e UIs trabalham em diretórios como unidades fundamentais. Amarrar a unidade fundamental do Go—o package—à estrutura do sistema de arquivos significa que ferramentas do sistema de arquivos se tornam ferramentas de package Go. Copiar, mover ou excluir um package corresponde a copiar, mover ou excluir um diretório.

Quarto, cada package é compilado usando apenas as informações presentes nos arquivos fonte. Isso torna muito mais provável que a ferramenta seja capaz de se adaptar a ambientes e condições de build em mudança. Por exemplo, se permitíssemos configuração extra como flags de compilador ou receitas de linha de comando, então aquela configuração precisaria ser atualizada cada vez que as ferramentas de build mudassem; também seria inerentemente amarrada ao uso de uma toolchain específica.

Começando com o comando go

Finalmente, um tour rápido de como usar o comando go. Como mencionado acima, o $GOPATH padrão no Unix é $HOME/go. Vamos armazenar nossos programas lá. Para usar um local diferente, você pode definir $GOPATH; veja How to Write Go Code para detalhes.

Primeiro adicionamos algum código fonte. Suponha que queremos usar a biblioteca de indexação do projeto codesearch junto com uma árvore vermelho-preta inclinada à esquerda. Podemos instalar ambas com o subcomando "go get":

$ go get github.com/google/codesearch/index
$ go get github.com/petar/GoLLRB/llrb
$

Ambos esses projetos estão agora baixados e instalados em $HOME/go, que contém os dois diretórios src/github.com/google/codesearch/index/ e src/github.com/petar/GoLLRB/llrb/, junto com os packages compilados (em pkg/) para essas bibliotecas e suas dependências.

Como usamos sistemas de controle de versão (Mercurial e Git) para fazer checkout dos sources, a árvore source também contém os outros arquivos nos repositórios correspondentes, como packages relacionados. O subcomando "go list" lista os caminhos de import correspondentes a seus argumentos, e o padrão "./..." significa começar no diretório atual ("./") e encontrar todos os packages abaixo daquele diretório ("..."):

$ cd $HOME/go/src
$ go list ./...
github.com/google/codesearch/cmd/cgrep
github.com/google/codesearch/cmd/cindex
github.com/google/codesearch/cmd/csearch
github.com/google/codesearch/index
github.com/google/codesearch/regexp
github.com/google/codesearch/sparse
github.com/petar/GoLLRB/example
github.com/petar/GoLLRB/llrb
$

Também podemos testar esses packages:

$ go test ./...
?   	github.com/google/codesearch/cmd/cgrep	[no test files]
?   	github.com/google/codesearch/cmd/cindex	[no test files]
?   	github.com/google/codesearch/cmd/csearch	[no test files]
ok  	github.com/google/codesearch/index	0.203s
ok  	github.com/google/codesearch/regexp	0.017s
?   	github.com/google/codesearch/sparse	[no test files]
?       github.com/petar/GoLLRB/example          [no test files]
ok      github.com/petar/GoLLRB/llrb             0.231s
$

Se um subcomando go é invocado sem caminhos listados, ele opera no diretório atual:

$ cd github.com/google/codesearch/regexp
$ go list
github.com/google/codesearch/regexp
$ go test -v
=== RUN   TestNstateEnc
--- PASS: TestNstateEnc (0.00s)
=== RUN   TestMatch
--- PASS: TestMatch (0.00s)
=== RUN   TestGrep
--- PASS: TestGrep (0.00s)
PASS
ok  	github.com/google/codesearch/regexp	0.018s
$ go install
$

Aquele subcomando "go install" instala a cópia mais recente do package no diretório pkg. Como o comando go pode analisar o grafo de dependências, "go install" também instala quaisquer packages que este package importa mas que estão desatualizados, recursivamente.

Note que "go install" foi capaz de determinar o nome do caminho de import para o package no diretório atual, por causa da convenção para nomeação de diretório. Seria um pouco mais conveniente se pudéssemos escolher o nome do diretório onde mantemos código fonte, e provavelmente não escolheríamos um nome tão longo, mas essa habilidade requereria configuração e complexidade adicional na ferramenta. Digitar um diretório extra ou dois é um pequeno preço a pagar pela simplicidade e poder aumentados.

Limitações

Como mencionado acima, o comando go não é uma ferramenta de build de propósito geral. Em particular, ele não tem nenhuma facilidade para gerar arquivos fonte Go durante um build, embora forneça go generate, que pode automatizar a criação de arquivos Go antes do build. Para setups de build mais avançados, você pode precisar escrever um makefile (ou um arquivo de configuração para a ferramenta de build de sua escolha) para executar qualquer ferramenta que crie os arquivos Go e então fazer check-in desses arquivos fonte gerados em seu repositório. Isso é mais trabalho para você, o autor do package, mas é significativamente menos trabalho para seus usuários, que podem usar "go get" sem precisar obter e compilar quaisquer ferramentas adicionais.
