Este documento explica como usar gccgo, um compilador para a linguagem Go. O compilador gccgo é um novo frontend para GCC, o amplamente utilizado compilador GNU. Embora o frontend em si esteja sob uma licença estilo BSD, gccgo é normalmente usado como parte do GCC e é então coberto pela GNU General Public License (a licença cobre o próprio gccgo como parte do GCC; ela não cobre código gerado pelo gccgo).

Note que gccgo não é o compilador gc; veja as instruções de Instalação do Go para aquele compilador.

Releases

A maneira mais simples de instalar gccgo é instalar um release binário do GCC construído para incluir suporte a Go. Releases binários do GCC estão disponíveis em vários sites e são tipicamente incluídos como parte de distribuições GNU/Linux. Esperamos que a maioria das pessoas que constroem esses binários incluam suporte a Go.

O release GCC 4.7.1 e todos os releases 4.7 posteriores incluem um compilador e bibliotecas Go 1 completos.

Devido ao timing, os releases GCC 4.8.0 e 4.8.1 são próximos mas não idênticos ao Go 1.1. O release GCC 4.8.2 inclui uma implementação completa do Go 1.1.2.

Os releases GCC 4.9 incluem uma implementação completa do Go 1.2.

Os releases GCC 5 incluem uma implementação completa das bibliotecas de usuário do Go 1.4. O runtime do Go 1.4 não está totalmente mesclado, mas isso não deve ser visível para programas Go.

Os releases GCC 6 incluem uma implementação completa das bibliotecas de usuário do Go 1.6.1. O runtime do Go 1.6 não está totalmente mesclado, mas isso não deve ser visível para programas Go.

Os releases GCC 7 incluem uma implementação completa das bibliotecas de usuário do Go 1.8.1. Como nos releases anteriores, o runtime do Go 1.8 não está totalmente mesclado, mas isso não deve ser visível para programas Go.

Os releases GCC 8 incluem uma implementação completa do release Go 1.10.1. O runtime do Go 1.10 agora foi totalmente mesclado nas fontes de desenvolvimento do GCC, e garbage collection concorrente é totalmente suportada.

Os releases GCC 9 incluem uma implementação completa do release Go 1.12.2.

Os releases GCC 10 incluem uma implementação completa do release Go 1.14.6.

Os releases GCC 11 incluem uma implementação completa do release Go 1.16.3.

Os releases GCC 12 e 13 incluem uma implementação completa da biblioteca padrão do Go 1.18. No entanto, o GCC ainda não inclui suporte para generics.

Código fonte

Se você não pode usar um release, ou prefere construir o gccgo você mesmo, o código fonte do gccgo é acessível via Git. O site do GCC tem instruções para obter o código fonte do GCC. O código fonte do gccgo está incluído. Como conveniência, uma versão estável do suporte a Go está disponível no branch devel/gccgo do repositório principal de código do GCC: git://gcc.gnu.org/git/gcc.git. Este branch é periodicamente atualizado com fontes estáveis do compilador Go.

Note que embora gcc.gnu.org seja a maneira mais conveniente de obter o código fonte para o frontend Go, não é onde as fontes mestras vivem. Se você quiser contribuir mudanças para o compilador frontend Go, veja Contribuindo para gccgo.

Construindo

Construir gccgo é como construir GCC com uma ou duas opções adicionais. Veja as instruções no site do gcc. Quando você executar configure, adicione a opção --enable-languages=c,c++,go (junto com outras linguagens que você possa querer construir). Se você estiver visando um x86 de 32 bits, então você vai querer construir gccgo para padronizar suporte a instruções compare and exchange bloqueadas; faça isso também usando a opção configure --with-arch=i586 (ou uma arquitetura mais nova, dependendo de onde você precisa que seus programas rodem). Se você estiver visando um x86 de 64 bits, mas às vezes quiser usar a opção -m32, então use a opção configure --with-arch-32=i586.

Gold

Em sistemas x86 GNU/Linux o compilador gccgo é capaz de usar uma pequena stack descontígua para goroutines. Isso permite que programas executem muito mais goroutines, já que cada goroutine pode usar uma stack relativamente pequena. Fazer isso requer usar o linker gold versão 2.22 ou posterior. Você pode instalar GNU binutils 2.22 ou posterior, ou você pode construir o gold você mesmo.

Para construir o gold você mesmo, construa o GNU binutils, usando --enable-gold=default quando você executar o script configure. Antes de construir, você deve instalar os packages flex e bison. Uma sequência típica seria assim (você pode substituir /opt/gold por qualquer diretório ao qual você tenha acesso de escrita): 

git clone git://sourceware.org/git/binutils-gdb.git
mkdir binutils-objdir
cd binutils-objdir
../binutils-gdb/configure --enable-gold=default --prefix=/opt/gold
make
make install

Independentemente de como você instale o gold, quando você configurar o gccgo, use a opção --with-ld=GOLD_BINARY.

Pré-requisitos

Vários pré-requisitos são necessários para construir o GCC, como descrito no site do gcc. É importante instalar todos os pré-requisitos antes de executar o script configure do gcc. As bibliotecas de pré-requisitos podem ser convenientemente baixadas usando o script contrib/download_prerequisites nas fontes do GCC.

Comandos de build

Uma vez que todos os pré-requisitos estejam instalados, então uma sequência típica de build e instalação seria assim (use apenas a opção --with-ld se você estiver usando o linker gold como descrito acima): 

git clone --branch devel/gccgo git://gcc.gnu.org/git/gcc.git gccgo
mkdir objdir
cd objdir
../gccgo/configure --prefix=/opt/gccgo --enable-languages=c,c++,go --with-ld=/opt/gold/bin/ld
make
make install

Usando gccgo

O compilador gccgo funciona como outros frontends gcc. A partir do GCC 5 a instalação do gccgo também inclui uma versão do comando go, que pode ser usado para construir programas Go como descrito em https://go.dev/cmd/go.

Para compilar um arquivo sem usar o comando go: 

gccgo -c file.go

Isso produz file.o. Para linkar arquivos juntos para formar um executável: 

gccgo -o file file.o

Para executar o arquivo resultante, você precisará dizer ao programa onde encontrar os packages Go compilados. Existem algumas maneiras de fazer isso:

  • Defina a variável de ambiente LD_LIBRARY_PATH: 

    LD_LIBRARY_PATH=${prefix}/lib/gcc/MACHINE/VERSION
[or]
LD_LIBRARY_PATH=${prefix}/lib64/gcc/MACHINE/VERSION
export LD_LIBRARY_PATH

    Aqui ${prefix} é a opção --prefix usada ao construir gccgo. Para uma instalação binária isso é normalmente /usr. Se deve usar lib ou lib64 depende do alvo. Tipicamente lib64 é correto para sistemas x86_64, e lib é correto para outros sistemas. A ideia é nomear o diretório onde libgo.so é encontrado.

  • Passando uma opção -Wl,-R quando você linkar (substitua lib por lib64 se apropriado para seu sistema): 

    go build -gccgoflags -Wl,-R,${prefix}/lib/gcc/MACHINE/VERSION
[or]
gccgo -o file file.o -Wl,-R,${prefix}/lib/gcc/MACHINE/VERSION

  • Use a opção -static-libgo para linkar estaticamente contra os packages compilados.

  • Use a opção -static para fazer um link totalmente estático (o padrão para o compilador gc).

Opções

O compilador gccgo suporta todas as opções do GCC que são independentes de linguagem, notavelmente as opções -O e -g.

A opção -fgo-pkgpath=PKGPATH pode ser usada para definir um prefixo único para o package sendo compilado. Esta opção é automaticamente usada pelo comando go, mas você pode querer usá-la se você invocar gccgo diretamente. Esta opção é destinada para uso com programas grandes que contêm muitos packages, a fim de permitir que múltiplos packages usem o mesmo identificador como nome do package. O PKGPATH pode ser qualquer string; uma boa escolha para a string é o caminho usado para importar o package.

As opções -I e -L, que são sinônimos para o compilador, podem ser usadas para definir o caminho de busca para encontrar imports. Essas opções não são necessárias se você construir com o comando go.

Imports

Quando você compila um arquivo que exporta algo, a informação de exportação será armazenada diretamente no arquivo objeto. Se você construir com gccgo diretamente, em vez de com o comando go, então quando você importar um package, você deve dizer ao gccgo como encontrar o arquivo.

Quando você importar o package FILE com gccgo, ele procurará pelos dados de importação nos seguintes arquivos, e usará o primeiro que encontrar.

  • FILE.gox
  • libFILE.so
  • libFILE.a
  • FILE.o

FILE.gox, quando usado, tipicamente conterá nada além de dados de exportação. Isso pode ser gerado de FILE.o via 

objcopy -j .go_export FILE.o FILE.gox

O compilador gccgo procurará no diretório atual por arquivos de importação. Em cenários mais complexos você pode passar a opção -I ou -L para gccgo. Ambas as opções recebem diretórios para pesquisar. A opção -L também é passada para o linker.

O compilador gccgo atualmente (2015-06-15) não registra o nome do arquivo de packages importados no arquivo objeto. Você deve providenciar para que os dados importados sejam linkados no programa. Novamente, isso não é necessário ao construir com o comando go. 

gccgo -c mypackage.go              # Exports mypackage
gccgo -c main.go                   # Imports mypackage
gccgo -o main main.o mypackage.o   # Explicitly links with mypackage.o

Debugging

Se você usar a opção -g quando você compilar, você pode executar gdb no seu executável. O debugger tem apenas conhecimento limitado sobre Go. Você pode definir breakpoints, executar passo-a-passo, etc. Você pode imprimir variáveis, mas elas serão impressas como se tivessem tipos C/C++. Para tipos numéricos isso não importa. Strings e interfaces Go aparecerão como estruturas de dois elementos. Maps e channels Go são sempre representados como ponteiros C para estruturas de runtime.

Interoperabilidade com C

Ao usar gccgo há interoperabilidade limitada com C, ou com código C++ compilado usando extern "C".

Tipos

Tipos básicos mapeiam diretamente: um int32 em Go é um int32_t em C, um int64 é um int64_t, etc. O tipo int do Go é um inteiro que é do mesmo tamanho que um ponteiro, e como tal corresponde ao tipo C intptr_t. byte do Go é equivalente a C unsigned char. Ponteiros em Go são ponteiros em C. Um struct do Go é o mesmo que C struct com os mesmos campos e tipos.

O tipo string do Go é atualmente definido como uma estrutura de dois elementos (isso está sujeito a mudanças): 

struct __go_string {
  const unsigned char *__data;
  intptr_t __length;
};

Você não pode passar arrays entre C e Go. No entanto, um ponteiro para um array em Go é equivalente a um ponteiro C para o equivalente do tipo do elemento. Por exemplo, Go *[10]int é equivalente a C int*, assumindo que o ponteiro C realmente aponte para 10 elementos.

Um slice em Go é uma estrutura. A definição atual é (isso está sujeito a mudanças): 

struct __go_slice {
  void *__values;
  intptr_t __count;
  intptr_t __capacity;
};

O tipo de uma função Go é um ponteiro para uma struct (isso está sujeito a mudanças). O primeiro campo na struct aponta para o código da função, que será equivalente a um ponteiro para uma função C cujos tipos de parâmetro são equivalentes, com um parâmetro adicional no final. O parâmetro no final é o closure, e o argumento a passar é um ponteiro para a struct da função Go. Quando uma função Go retorna mais de um valor, a função C retorna uma struct. Por exemplo, essas funções são aproximadamente equivalentes: 

func GoFunction(int) (int, float64)
struct { int i; float64 f; } CFunction(int, void*)

Os tipos interface, channel e map do Go não têm tipo C correspondente (interface é uma estrutura de dois elementos e channel e map são ponteiros para structs em C, mas as structs são deliberadamente não documentadas). Tipos enum de C correspondem a algum tipo inteiro, mas precisamente qual é difícil de prever em geral; use um cast. Tipos union de C não têm tipo Go correspondente. Tipos struct de C contendo bitfields não têm tipo Go correspondente. Tipos class de C++ não têm tipo Go correspondente.

Alocação de memória é completamente diferente entre C e Go, já que Go usa garbage collection. As diretrizes exatas nesta área são indeterminadas, mas é provável que seja permitido passar um ponteiro para memória alocada de C para Go. A responsabilidade de eventualmente liberar o ponteiro permanecerá com o lado C, e claro se o lado C liberar o ponteiro enquanto o lado Go ainda tiver uma cópia o programa falhará. Ao passar um ponteiro de Go para C, a função Go deve reter uma cópia visível dele em alguma variável Go. Caso contrário o garbage collector do Go pode deletar o ponteiro enquanto a função C ainda está usando-o.

Nomes de função

Código Go pode chamar funções C diretamente usando uma extensão Go implementada no gccgo: uma declaração de função pode ser precedida por //extern NAME. Por exemplo, aqui está como a função C open pode ser declarada em Go: 

//extern open
func c_open(name *byte, mode int, perm int) int

A função C naturalmente espera uma string terminada em NUL, que em Go é equivalente a um ponteiro para um array (não um slice!) de byte com um byte zero no final. Então uma chamada exemplo de Go seria (após importar o package syscall): 

var name = [4]byte{'f', 'o', 'o', 0};
i := c_open(&name[0], syscall.O_RDONLY, 0);

(isso serve apenas como exemplo, para abrir um arquivo em Go por favor use a função os.Open do Go em vez disso).

Note que se a função C pode bloquear, como em uma chamada a read, chamar a função C pode bloquear o programa Go. A menos que você tenha uma compreensão clara do que está fazendo, todas as chamadas entre C e Go devem ser implementadas através de cgo ou SWIG, como para o compilador gc.

O nome de funções Go acessadas de C está sujeito a mudanças. No momento o nome de uma função Go que não tem um receiver é prefix.package.Functionname. O prefixo é definido pela opção -fgo-prefix usada quando o package é compilado; se a opção não for usada, o padrão é go. Para chamar a função de C você deve definir o nome usando uma extensão do GCC. 

extern int go_function(int) __asm__ ("myprefix.mypackage.Function");

Geração automática de declarações Go a partir de código fonte C

A versão Go do GCC suporta gerar automaticamente declarações Go a partir de código C. A funcionalidade é bastante desajeitada, e a maioria dos usuários deveria usar o programa cgo com a opção -gccgo em vez disso.

Compile seu código C como de costume, e adicione a opção -fdump-go-spec=FILENAME. Isso criará o arquivo FILENAME como efeito colateral da compilação. Este arquivo conterá declarações Go para os tipos, variáveis e funções declaradas no código C. Tipos C que não podem ser representados em Go serão registrados como comentários no código Go. O arquivo gerado não terá uma declaração package, mas pode de outra forma ser compilado diretamente pelo gccgo.

Este procedimento está cheio de advertências e restrições não declaradas e não fazemos garantia de que ele não mudará no futuro. É mais útil como um ponto de partida para código Go real do que como um procedimento regular.
