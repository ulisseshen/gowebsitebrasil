Introdução

O ecossistema Go fornece um grande conjunto de APIs e ferramentas para diagnosticar problemas de lógica e desempenho em programas Go. Esta página resume as ferramentas disponíveis e ajuda usuários Go a escolher a correta para seu problema específico.

Soluções de diagnóstico podem ser categorizadas nos seguintes grupos:

  • Profiling: Ferramentas de profiling analisam a complexidade e custos de um programa Go, como seu uso de memória e funções frequentemente chamadas, para identificar as seções caras de um programa Go.
  • Tracing: Tracing é uma maneira de instrumentar código para analisar latência ao longo do ciclo de vida de uma chamada ou solicitação de usuário. Traces fornecem uma visão geral de quanta latência cada componente contribui para a latência geral em um sistema. Traces podem abranger vários processos Go.
  • Debugging: Debugging nos permite pausar um programa Go e examinar sua execução. O estado e fluxo do programa podem ser verificados com debugging.
  • Estatísticas e eventos de runtime: Coleta e análise de estatísticas e eventos de runtime fornecem uma visão geral de alto nível da saúde de programas Go. Picos/quedas de métricas nos ajudam a identificar mudanças em throughput, utilização e desempenho.

Nota: Algumas ferramentas de diagnóstico podem interferir umas com as outras. Por exemplo, profiling preciso de memória distorce profiles de CPU e profiling de bloqueio de goroutine afeta o trace do scheduler. Use ferramentas isoladamente para obter informações mais precisas.

Profiling

Profiling é útil para identificar seções caras ou frequentemente chamadas de código. O runtime Go fornece dados de profiling no formato esperado pela ferramenta de visualização pprof. Os dados de profiling podem ser coletados durante testes via go test ou endpoints disponibilizados pelo pacote net/http/pprof. Usuários precisam coletar os dados de profiling e usar ferramentas pprof para filtrar e visualizar os principais caminhos de código.

Profiles predefinidos fornecidos pelo pacote runtime/pprof:

  • cpu: Profile de CPU determina onde um programa gasta seu tempo enquanto consome ativamente ciclos de CPU (em oposição a enquanto dorme ou aguarda I/O).
  • heap: Profile de heap relata amostras de alocação de memória; usado para monitorar uso atual e histórico de memória, e para verificar vazamentos de memória.
  • threadcreate: Profile de criação de thread relata as seções do programa que levam à criação de novas threads do OS.
  • goroutine: Profile de goroutine relata os stack traces de todas as goroutines atuais.
  • block: Profile de bloqueio mostra onde goroutines bloqueiam aguardando primitivas de sincronização (incluindo timer channels). Profile de bloqueio não está habilitado por padrão; use runtime.SetBlockProfileRate para habilitá-lo.
  • mutex: Profile de mutex relata contenções de lock. Quando você acha que sua CPU não está totalmente utilizada devido a contenção de mutex, use este profile. Profile de mutex não está habilitado por padrão, veja runtime.SetMutexProfileFraction para habilitá-lo.

Quais outros profilers posso usar para fazer profile de programas Go?

No Linux, ferramentas perf podem ser usadas para fazer profiling de programas Go. Perf pode fazer profile de e unwind código cgo/SWIG e kernel, então pode ser útil para obter insights sobre gargalos de desempenho nativos/kernel. No macOS, a suite Instruments pode ser usada para fazer profile de programas Go.

Posso fazer profile dos meus serviços em produção?

Sim. É seguro fazer profile de programas em produção, mas habilitar alguns profiles (por exemplo, o profile de CPU) adiciona custo. Você deve esperar ver degradação de desempenho. A penalidade de desempenho pode ser estimada medindo o overhead do profiler antes de ligá-lo em produção.

Você pode querer fazer profile periodicamente dos seus serviços em produção. Especialmente em um sistema com muitas réplicas de um único processo, selecionar uma réplica aleatória periodicamente é uma opção segura. Selecione um processo em produção, faça profile dele por X segundos a cada Y segundos e salve os resultados para visualização e análise; então repita periodicamente. Resultados podem ser manual e/ou automaticamente revisados para encontrar problemas. Coleta de profiles pode interferir uns com os outros, então é recomendado coletar apenas um profile de cada vez.

Estou restrito aos profiles integrados?

Além do que é fornecido pelo runtime, usuários Go podem criar seus profiles customizados via pprof.Profile e usar as ferramentas existentes para examiná-los.

Posso servir os handlers de profiler (/debug/pprof/...) em um caminho e porta diferentes?

Sim. O pacote net/http/pprof registra seus handlers no mux padrão por padrão, mas você também pode registrá-los você mesmo usando os handlers exportados do pacote.

Por exemplo, o seguinte exemplo servirá o handler pprof.Profile em :7777 em /custom_debug_path/profile: 

package main

import (
	"log"
	"net/http"
	"net/http/pprof"
)

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("/custom_debug_path/profile", pprof.Profile)
	log.Fatal(http.ListenAndServe(":7777", mux))
}

Tracing

Tracing é uma maneira de instrumentar código para analisar latência ao longo do ciclo de vida de uma cadeia de chamadas. Go fornece o pacote golang.org/x/net/trace como um backend de tracing mínimo por nó Go e fornece uma biblioteca de instrumentação mínima com um painel simples. Go também fornece um tracer de execução para rastrear os eventos de runtime dentro de um intervalo.

Tracing nos permite:

  • Instrumentar e analisar latência de aplicação em um processo Go.
  • Medir o custo de chamadas específicas em uma longa cadeia de chamadas.
  • Descobrir a utilização e melhorias de desempenho. Gargalos nem sempre são óbvios sem dados de tracing.

Em sistemas monolíticos, é relativamente fácil coletar dados de diagnóstico dos blocos de construção de um programa. Todos os módulos vivem dentro de um processo e compartilham recursos comuns para relatar logs, erros e outras informações de diagnóstico. Uma vez que seu sistema cresce além de um único processo e começa a se tornar distribuído, torna-se mais difícil seguir uma chamada começando do servidor web front-end até todos os seus back-ends até que uma resposta seja retornada de volta ao usuário. É aqui que tracing distribuído desempenha um grande papel para instrumentar e analisar seus sistemas em produção.

Tracing distribuído é uma maneira de instrumentar código para analisar latência ao longo do ciclo de vida de uma solicitação de usuário. Quando um sistema é distribuído e quando ferramentas convencionais de profiling e debugging não escalam, você pode querer usar ferramentas de tracing distribuído para analisar o desempenho de suas solicitações de usuário e RPCs.

Tracing distribuído nos permite:

  • Instrumentar e fazer profile de latência de aplicação em um sistema grande.
  • Rastrear todos os RPCs dentro do ciclo de vida de uma solicitação de usuário e ver problemas de integração que são visíveis apenas em produção.
  • Descobrir melhorias de desempenho que podem ser aplicadas aos nossos sistemas. Muitos gargalos não são óbvios antes da coleta de dados de tracing.

O ecossistema Go fornece várias bibliotecas de tracing distribuído por sistema de tracing e agnósticas de backend.

Existe uma maneira de interceptar automaticamente cada chamada de função e criar traces?

Go não fornece uma maneira de interceptar automaticamente cada chamada de função e criar trace spans. Você precisa instrumentar manualmente seu código para criar, finalizar e anotar spans.

Como devo propagar headers de trace em bibliotecas Go?

Você pode propagar identificadores e tags de trace no context.Context. Ainda não há uma chave de trace canônica ou representação comum de headers de trace na indústria. Cada provedor de tracing é responsável por fornecer utilitários de propagação em suas bibliotecas Go.

Quais outros eventos de baixo nível da biblioteca padrão ou runtime podem ser incluídos em um trace?

A biblioteca padrão e o runtime estão tentando expor várias APIs adicionais para notificar sobre eventos internos de baixo nível. Por exemplo, httptrace.ClientTrace fornece APIs para seguir eventos de baixo nível no ciclo de vida de uma solicitação de saída. Há um esforço contínuo para recuperar eventos de runtime de baixo nível do tracer de execução de runtime e permitir que usuários definam e gravem seus eventos de usuário.

Debugging

Debugging é o processo de identificar por que um programa se comporta mal. Debuggers nos permitem entender o fluxo de execução e estado atual de um programa. Existem vários estilos de debugging; esta seção focará apenas em anexar um debugger a um programa e debugging de core dump.

Usuários Go usam principalmente os seguintes debuggers:

  • Delve: Delve é um debugger para a linguagem de programação Go. Ele tem suporte para conceitos de runtime do Go e tipos integrados. Delve está tentando ser um debugger confiável e completo para programas Go.
  • GDB: Go fornece suporte GDB via o compilador Go padrão e Gccgo. O gerenciamento de stack, threading e runtime contêm aspectos que diferem suficientemente do modelo de execução que o GDB espera que possam confundir o debugger, mesmo quando o programa é compilado com gccgo. Embora o GDB possa ser usado para fazer debug de programas Go, não é ideal e pode criar confusão.

Quão bem os debuggers funcionam com programas Go?

O compilador gc realiza otimizações como inlining de função e registerização de variável. Essas otimizações às vezes tornam o debugging com debuggers mais difícil. Há um esforço contínuo para melhorar a qualidade das informações DWARF geradas para binários otimizados. Até que essas melhorias estejam disponíveis, recomendamos desabilitar otimizações ao compilar o código sendo debugado. O seguinte comando compila um pacote sem otimizações de compilador: 

$ go build -gcflags=all="-N -l"

Como parte do esforço de melhoria, Go 1.10 introduziu uma nova flag de compilador -dwarflocationlists. A flag faz com que o compilador adicione listas de localização que ajudam debuggers a trabalhar com binários otimizados. O seguinte comando compila um pacote com otimizações mas com as listas de localização DWARF: 

$ go build -gcflags="-dwarflocationlists=true"

Qual é a interface de usuário de debugger recomendada?

Embora tanto delve quanto gdb forneçam CLIs, a maioria das integrações de editor e IDEs fornecem interfaces de usuário específicas para debugging.

É possível fazer debugging postmortem com programas Go?

Um arquivo de core dump é um arquivo que contém o dump de memória de um processo em execução e seu status de processo. É usado principalmente para debugging postmortem de um programa e para entender seu estado enquanto ainda está em execução. Esses dois casos tornam o debugging de core dumps uma boa ajuda de diagnóstico para postmortem e analisar serviços em produção. É possível obter arquivos core de programas Go e usar delve ou gdb para fazer debug, veja a página debugging de core dump para um guia passo a passo.

Estatísticas e eventos de runtime

O runtime fornece estatísticas e relatórios de eventos internos para usuários diagnosticarem problemas de desempenho e utilização no nível de runtime.

Usuários podem monitorar essas estatísticas para entender melhor a saúde geral e desempenho de programas Go. Algumas estatísticas e estados frequentemente monitorados:

  • runtime.ReadMemStats relata as métricas relacionadas à alocação de heap e garbage collection. Estatísticas de memória são úteis para monitorar quantos recursos de memória um processo está consumindo, se o processo pode utilizar memória bem, e para detectar vazamentos de memória.
  • debug.ReadGCStats lê estatísticas sobre garbage collection. É útil para ver quanto dos recursos são gastos em pausas de GC. Também relata uma linha do tempo de pausas do garbage collector e percentis de tempo de pausa.
  • debug.Stack retorna o stack trace atual. Stack trace é útil para ver quantas goroutines estão atualmente em execução, o que elas estão fazendo, e se estão bloqueadas ou não.
  • debug.WriteHeapDump suspende a execução de todas as goroutines e permite fazer dump do heap para um arquivo. Um heap dump é um snapshot da memória de um processo Go em um determinado momento. Contém todos os objetos alocados, bem como goroutines, finalizers e mais.
  • runtime.NumGoroutine retorna o número de goroutines atuais. O valor pode ser monitorado para ver se goroutines suficientes estão sendo utilizadas, ou para detectar vazamentos de goroutine.

Execution tracer

Go vem com um tracer de execução de runtime para capturar uma ampla gama de eventos de runtime. Agendamento, syscall, garbage collections, tamanho de heap e outros eventos são coletados pelo runtime e disponíveis para visualização pelo go tool trace. Execution tracer é uma ferramenta para detectar problemas de latência e utilização. Você pode examinar quão bem a CPU está sendo utilizada, e quando networking ou syscalls são uma causa de preempção para as goroutines.

Tracer é útil para:

  • Entender como suas goroutines executam.
  • Entender alguns dos principais eventos de runtime como execuções de GC.
  • Identificar execução mal paralelizada.

No entanto, não é ótimo para identificar hot spots como analisar a causa de uso excessivo de memória ou CPU. Use ferramentas de profiling primeiro para resolvê-los.

GODEBUG

Runtime também emite eventos e informações se a variável de ambiente GODEBUG for definida adequadamente.

  • GODEBUG=gctrace=1 imprime eventos do garbage collector em cada coleta, resumindo a quantidade de memória coletada e o comprimento da pausa.
  • GODEBUG=inittrace=1 imprime um resumo do tempo de execução e informações de alocação de memória para trabalho de inicialização de pacote concluído.
  • GODEBUG=schedtrace=X imprime eventos de agendamento a cada X milissegundos.

A variável de ambiente GODEBUG pode ser usada para desabilitar o uso de extensões de conjunto de instruções na biblioteca padrão e runtime.

  • GODEBUG=cpu.all=off desabilita o uso de todas as extensões opcionais de conjunto de instruções.
  • GODEBUG=cpu.extension=off desabilita o uso de instruções da extensão de conjunto de instruções especificada.
    extension é o nome em minúsculas para a extensão de conjunto de instruções como sse41 ou avx.
