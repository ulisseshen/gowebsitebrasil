Introdução

O lançamento do Go versão 1, Go 1 para abreviar, é um marco importante no desenvolvimento da linguagem. Go 1 é uma plataforma estável para o crescimento de programas e projetos escritos em Go.

Go 1 define duas coisas: primeiro, a especificação da linguagem; e segundo, a especificação de um conjunto de APIs principais, os "pacotes padrão" da biblioteca Go. O lançamento do Go 1 inclui sua implementação na forma de duas suítes de compiladores (gc e gccgo), e as bibliotecas principais em si.

A intenção é que programas escritos para a especificação Go 1 continuem a compilar e executar corretamente, inalterados, ao longo da vida útil dessa especificação. Em algum ponto indefinido, uma especificação Go 2 pode surgir, mas até lá, programas Go que funcionam hoje devem continuar a funcionar mesmo quando futuros lançamentos "point" do Go 1 surgirem (Go 1.1, Go 1.2, etc.).

A compatibilidade é no nível do código-fonte. A compatibilidade binária para pacotes compilados não é garantida entre lançamentos. Após um lançamento point, o código-fonte Go precisará ser recompilado para vincular com o novo lançamento.

As APIs podem crescer, adquirindo novos pacotes e recursos, mas não de uma forma que quebre código Go 1 existente.

Expectativas

Embora esperemos que a grande maioria dos programas mantenha essa compatibilidade ao longo do tempo, é impossível garantir que nenhuma mudança futura quebrará qualquer programa. Este documento é uma tentativa de definir expectativas para a compatibilidade de software Go 1 no futuro. Há várias maneiras pelas quais um programa que compila e executa hoje pode falhar em fazê-lo após um futuro lançamento point. Todas são improváveis, mas vale a pena registrá-las.

  • Segurança. Um problema de segurança na especificação ou implementação pode vir à tona cuja resolução exija quebrar a compatibilidade. Reservamo-nos o direito de abordar tais problemas de segurança.
  • Comportamento não especificado. A especificação Go tenta ser explícita sobre a maioria das propriedades da linguagem, mas há alguns aspectos que são indefinidos. Programas que dependem de tal comportamento não especificado podem quebrar em lançamentos futuros.
  • Erros de especificação. Se for necessário abordar uma inconsistência ou incompletude na especificação, resolver o problema pode afetar o significado ou a legalidade de programas existentes. Reservamo-nos o direito de abordar tais problemas, incluindo atualizar as implementações. Exceto por problemas de segurança, nenhuma alteração incompatível na especificação seria feita.
  • Bugs. Se um compilador ou biblioteca tem um bug que viola a especificação, um programa que depende do comportamento com bug pode quebrar se o bug for corrigido. Reservamo-nos o direito de corrigir tais bugs.
  • Struct literals. Para a adição de recursos em lançamentos point posteriores, pode ser necessário adicionar campos a structs exportadas na API. Código que usa struct literals sem chaves (como pkg.T{3, "x"}) para criar valores desses tipos falharia ao compilar após tal mudança. No entanto, código que usa literals com chaves (pkg.T{A: 3, B: "x"}) continuará a compilar após tal mudança. Atualizaremos tais estruturas de dados de uma forma que permita que struct literals com chaves permaneçam compatíveis, embora literals sem chaves possam falhar ao compilar. (Há também casos mais intrincados envolvendo estruturas de dados aninhadas ou interfaces, mas eles têm a mesma resolução.) Portanto, recomendamos que literals compostos cujo tipo é definido em um pacote separado devam usar a notação com chaves.
  • Métodos. Assim como com campos de struct, pode ser necessário adicionar métodos a tipos que não são interface. Em algumas circunstâncias, como quando o tipo é incorporado em uma struct junto com outro tipo, a adição do novo método pode quebrar a struct criando um conflito com um método existente do outro tipo incorporado. Não podemos proteger contra este caso raro e não garantimos compatibilidade caso ele surja.
  • Dot imports. Se um programa importa um pacote padrão usando import . "path", nomes adicionais definidos no pacote importado em lançamentos futuros podem conflitar com outros nomes definidos no programa. Não recomendamos o uso de import . fora de testes, e usá-lo pode fazer com que um programa falhe ao compilar em lançamentos futuros.
  • Uso do pacote unsafe. Pacotes que importam unsafe podem depender de propriedades internas da implementação Go. Reservamo-nos o direito de fazer alterações na implementação que podem quebrar tais programas.

Claro, para todas essas possibilidades, caso surjam, nos esforçaríamos sempre que viável para atualizar a especificação, compiladores ou bibliotecas sem afetar código existente.

Essas mesmas considerações se aplicam a lançamentos point sucessivos. Por exemplo, código que executa no Go 1.2 deve ser compatível com Go 1.2.1, Go 1.3, Go 1.4, etc., embora não necessariamente com Go 1.1 já que pode usar recursos adicionados apenas no Go 1.2

Recursos adicionados entre lançamentos, disponíveis no repositório de código-fonte mas que não fazem parte dos lançamentos binários numerados, estão sob desenvolvimento ativo. Nenhuma promessa de compatibilidade é feita para software usando tais recursos até que eles tenham sido lançados.

Finalmente, embora não seja uma questão de correção, é possível que o desempenho de um programa possa ser afetado por mudanças na implementação dos compiladores ou bibliotecas dos quais ele depende. Nenhuma garantia pode ser feita sobre o desempenho de um programa específico entre lançamentos.

Embora essas expectativas se apliquem ao próprio Go 1, esperamos que considerações semelhantes sejam feitas para o desenvolvimento de software externamente desenvolvido baseado em Go 1.

Sub-repositórios

Código em sub-repositórios da árvore principal do go, como golang.org/x/net, pode ser desenvolvido sob requisitos de compatibilidade mais flexíveis. No entanto, os sub-repositórios serão marcados conforme apropriado para identificar versões que são compatíveis com os lançamentos point do Go 1.

Sistemas operacionais

É impossível garantir compatibilidade a longo prazo com interfaces de sistema operacional, que são alteradas por terceiros. O pacote syscall está, portanto, fora do escopo das garantias feitas aqui. A partir da versão Go 1.4, o pacote syscall está congelado. Qualquer evolução da interface de chamada do sistema deve ser suportada em outro lugar, como no sub-repositório go.sys. Para detalhes e contexto, veja este documento.

Ferramentas

Finalmente, a toolchain Go (compiladores, linkers, ferramentas de build, e assim por diante) está sob desenvolvimento ativo e pode mudar de comportamento. Isso significa, por exemplo, que scripts que dependem da localização e propriedades das ferramentas podem ser quebrados por um lançamento point.

Essas ressalvas à parte, acreditamos que Go 1 será uma base sólida para o desenvolvimento do Go e seu ecossistema.
