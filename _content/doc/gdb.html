As seguintes instruções se aplicam à toolchain padrão (o compilador e ferramentas gc Go). Gccgo tem suporte nativo a gdb.

Note que Delve é uma alternativa melhor ao GDB ao debugar programas Go construídos com a toolchain padrão. Ele entende o runtime Go, estruturas de dados e expressões melhor que o GDB. Delve atualmente suporta Linux, OSX, e Windows em amd64. Para a lista mais atualizada de plataformas suportadas, por favor veja a documentação do Delve.

GDB não entende programas Go muito bem. O gerenciamento de stack, threading e runtime contêm aspectos que diferem o suficiente do modelo de execução que o GDB espera que possam confundir o debugger e causar resultados incorretos mesmo quando o programa é compilado com gccgo. Como consequência, embora o GDB possa ser útil em algumas situações (por exemplo, debugging de código Cgo, ou debugging do próprio runtime), não é um debugger confiável para programas Go, particularmente aqueles altamente concorrentes. Além disso, não é uma prioridade para o projeto Go resolver estes problemas, que são difíceis.

Em resumo, as instruções abaixo devem ser tomadas apenas como um guia de como usar GDB quando ele funciona, não como uma garantia de sucesso. Além desta visão geral você pode querer consultar o manual do GDB.

Introdução

Quando você compila e linka seus programas Go com a toolchain gc no Linux, macOS, FreeBSD ou NetBSD, os binários resultantes contêm informações de debugging DWARFv4 que versões recentes (≥7.5) do debugger GDB podem usar para inspecionar um processo vivo ou um core dump.

Passe a flag '-w' para o linker para omitir as informações de debug (por exemplo, go build -ldflags=-w prog.go).

O código gerado pelo compilador gc inclui inlining de invocações de função e registerização de variáveis. Estas otimizações podem às vezes tornar debugging com gdb mais difícil. Se você achar que precisa desabilitar essas otimizações, construa seu programa usando go build -gcflags=all="-N -l".

Se você quiser usar gdb para inspecionar um core dump, pode disparar um dump em um crash de programa, em sistemas que permitem isso, definindo GOTRACEBACK=crash no ambiente (veja a documentação do package runtime para mais informações).

Operações Comuns

  • Mostrar arquivo e número de linha para código, definir breakpoints e desmontar: 
    (gdb) list
(gdb) list line
(gdb) list file.go:line
(gdb) break line
(gdb) break file.go:line
(gdb) disas
  • Mostrar backtraces e desempilhar stack frames: 
    (gdb) bt
(gdb) frame n
  • Mostrar o nome, tipo e localização no stack frame de variáveis locais, argumentos e valores de retorno: 
    (gdb) info locals
(gdb) info args
(gdb) p variable
(gdb) whatis variable
  • Mostrar o nome, tipo e localização de variáveis globais: 
    (gdb) info variables regexp

Extensões Go

Um mecanismo de extensão recente para GDB permite que ele carregue scripts de extensão para um dado binário. A toolchain usa isso para estender GDB com um punhado de comandos para inspecionar internals do código do runtime (como goroutines) e para pretty print dos tipos map, slice e channel builtin.

  • Pretty printing de uma string, slice, map, channel ou interface: 
    (gdb) p var
  • Uma função $len() e $cap() para strings, slices e maps: 
    (gdb) p $len(var)
  • Uma função para fazer cast de interfaces para seus tipos dinâmicos: 
    (gdb) p $dtype(var)
(gdb) iface var

    Issue conhecido: GDB não pode automaticamente encontrar o tipo dinâmico de um valor de interface se seu nome longo difere de seu nome curto (irritante ao imprimir stacktraces, o pretty printer cai de volta para imprimir o nome de tipo curto e um ponteiro).

  • Inspecionando goroutines: 
    (gdb) info goroutines
(gdb) goroutine n cmd
(gdb) help goroutine
    Por exemplo: 
    (gdb) goroutine 12 bt
    Você pode inspecionar todas as goroutines passando all em vez do ID de uma goroutine específica. Por exemplo: 
    (gdb) goroutine all bt

Se você gostaria de ver como isso funciona, ou quer estendê-lo, dê uma olhada em src/runtime/runtime-gdb.py na distribuição do código fonte Go. Ele depende de alguns tipos magic especiais (hash<T,U>) e variáveis (runtime.m e runtime.g) que o linker (src/cmd/link/internal/ld/dwarf.go) garante que estejam descritos no código DWARF.

Se você está interessado em como a informação de debugging se parece, execute objdump -W a.out e navegue pelas seções .debug_*.

Issues Conhecidos

  1. Pretty printing de string só dispara para tipo string, não para tipos derivados dele.
  2. Informação de tipo está faltando para as partes C da biblioteca runtime.
  3. GDB não entende qualificações de nome do Go e trata "fmt.Print" como um literal não estruturado com um "." que precisa ser entre aspas. Ele se opõe ainda mais fortemente a nomes de métodos do formato pkg.(*MyType).Meth.
  4. A partir do Go 1.11, informação de debug é comprimida por padrão. Versões mais antigas de gdb, como a disponível por padrão no MacOS, não entendem a compressão. Você pode gerar informação de debug não comprimida usando go build -ldflags=-compressdwarf=false. (Por conveniência você pode colocar a opção -ldflags na variável de ambiente GOFLAGS para não ter que especificá-la cada vez.)

Tutorial

Neste tutorial inspecionaremos o binário dos unit tests do package regexp. Para construir o binário, mude para $GOROOT/src/regexp e execute go test -c. Isso deve produzir um arquivo executável chamado regexp.test.

Começando

Lance o GDB, debugando regexp.test: 

$ gdb regexp.test

A mensagem "Loading Go Runtime support" significa que GDB carregou a extensão de $GOROOT/src/runtime/runtime-gdb.py.

Para ajudar GDB a encontrar os fontes do runtime Go e o script de suporte que o acompanha, passe seu $GOROOT com a flag '-d': 

$ gdb regexp.test -d $GOROOT

Se por alguma razão GDB ainda não consegue encontrar aquele diretório ou aquele script, você pode carregá-lo manualmente dizendo ao gdb (assumindo que você tem os fontes do go em ~/go/): 

(gdb) source ~/go/src/runtime/runtime-gdb.py
Loading Go Runtime support.

Inspecionando o código fonte

Use o comando "l" ou "list" para inspecionar código fonte. 

(gdb) l

Liste uma parte específica do fonte parametrizando "list" com um nome de função (ele deve ser qualificado com seu nome de package). 

(gdb) l main.main

Liste um arquivo e número de linha específicos: 

(gdb) l regexp.go:1
(gdb) # Pressione enter para repetir último comando. Aqui, isso lista próximas 10 linhas.

Nomenclatura

Nomes de variáveis e funções devem ser qualificados com o nome dos packages a que pertencem. A função Compile do package regexp é conhecida pelo GDB como 'regexp.Compile'.

Métodos devem ser qualificados com o nome de seus tipos receiver. Por exemplo, o método String do tipo *Regexp é conhecido como 'regexp.(*Regexp).String'.

Variáveis que sombreiam outras variáveis recebem magicamente um sufixo com um número na informação de debug. Variáveis referenciadas por closures aparecerão como ponteiros com prefixo mágico '&'.

Pretty Printing

O mecanismo de pretty printing do GDB é acionado por matches de regexp em nomes de tipo. Um exemplo para slices: 

(gdb) p utf
$22 =  []uint8 = {0 '\000', 0 '\000', 0 '\000', 0 '\000'}

Já que slices, arrays e strings não são ponteiros C, GDB não pode interpretar a operação de subscripting para você, mas você pode olhar dentro da representação runtime para fazer isso (tab completion ajuda aqui): 


(gdb) p slc
$11 =  []int = {0, 0}
(gdb) p slc-><TAB>
array  slc    len
(gdb) p slc->array
$12 = (int *) 0xf84057af00
(gdb) p slc->array[1]
$13 = 0

As funções de extensão $len e $cap funcionam em strings, arrays e slices: 

(gdb) p $len(utf)
$23 = 4
(gdb) p $cap(utf)
$24 = 4

Channels e maps são tipos 'reference', que gdb mostra como ponteiros para tipos tipo C++ hash<int,string>*. Desreferenciar disparará prettyprinting

Interfaces são representadas no runtime como um ponteiro para um descritor de tipo e um ponteiro para um valor. A extensão GDB runtime do Go decodifica isso e automaticamente dispara pretty printing para o tipo runtime. A função de extensão $dtype decodifica o tipo dinâmico para você (exemplos são tirados de um breakpoint em regexp.go linha 293.) 

(gdb) p i
$4 = {str = "cbb"}
(gdb) whatis i
type = regexp.input
(gdb) p $dtype(i)
$26 = (struct regexp.inputBytes *) 0xf8400b4930
(gdb) iface i
regexp.input: struct regexp.inputBytes *
